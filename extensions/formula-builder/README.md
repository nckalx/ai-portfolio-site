# Formula Builder extension (V1.0C — Phase 5 Batch 2)

A local Chrome/Chromium side panel for finding, configuring, and copying Smartsheet formulas. The UI is independent of the portfolio site. No installation of Node packages is needed.

## Package and load

From the repository root in PowerShell:

```powershell
npm run package:extension
```

Open `chrome://extensions`, enable Developer mode, choose **Load unpacked**, and select the generated **dist/formula-builder** directory. Pin the extension and click its toolbar action to open the panel. Chrome 114 or later is required; other Chromium browsers must implement Chrome's side-panel API.

After source changes, run the packaging command again, reload the extension on `chrome://extensions`, then reopen the panel. Do not load `extensions/formula-builder` directly: the shared core is added during packaging. Do not edit generated files.

The packager uses Node built-ins and an explicit 20-file allowlist. It copies source bytes without transpiling or bundling. It refuses unexpected entries in an existing output directory instead of deleting them; inspect and move those entries yourself before retrying. `/dist/formula-builder/` is ignored by Git. The README, tests, fixtures, portfolio UI, Schedule Analyzer, and source/reference icon are not shipped.

## Architecture and scope

- `js/formula-builder/` remains the single canonical source for the catalog, utilities, validation, guidance, and engine. The 26 Advanced formula types and all 44 reviewed Advanced combinations remain unchanged; 18 structured Common formulas bring the canonical catalog to 44 entries.
- The extension-only `theme.js` loads early in the document head. The seven shared classic scripts load from packaged `core/` in this order: catalog, utils, primitives, validation, guidance, common-builders, engine. They are followed by `formula-discovery.js`, `structured-fields.js`, and `sidepanel.js`. The application has no build system, runtime dependencies, network requests, or remote executable code.
- Discovery reads the canonical labels, explanations, keywords, and five categories. Search requires every whitespace-separated term to match user-facing metadata, ignores case, and preserves catalog order. Internal IDs and user values are not search terms.
- Extension discovery requires `availability.extension === true` and an exact primitive `libraryId` of `advanced` or `common`. Missing, malformed, or unknown library metadata is excluded without normalization or inference. The current availability metadata excludes `multiLineReportLabel` and `rioIdLookup`: exactly 24 Advanced formulas remain visible in their existing order. Both excluded formulas remain in the shared engine and 26-formula portfolio.
- Phase 5 Batches 1 and 2 provide 18 extension-only Common formulas: eight numeric formulas in Counts & calculations and ten text formulas in Text & labels. The native Library radio selector is visible. Advanced remains the startup preference with 24 choices; Common has 18, for 42 extension-visible formulas. The portfolio remains 26 Advanced formulas only.
- `findFormulas(catalog, categories, query, categoryId, libraryId = "advanced")` filters by surface, library, category, then search. Four-argument callers retain Advanced discovery. Unknown libraries/categories and empty libraries return no matches. The pure `resolveDiscoveryState()` separately recovers UI state: preserve a populated library, otherwise prefer Advanced, then Common, then no selection. Categories follow canonical order and include only categories populated in the selected library, independently of search.
- Library switches preserve the exact raw query and any category supported by the destination; otherwise the category visibly resets to All categories with no per-library memory. Both explicit Clear filters buttons clear query/category, keep the library, and focus search. Library selection alone does not enable Clear. Library state is panel-local and is never persisted or tied to drafts. Back reveals the existing Find DOM without rerendering results, preserving result focus and scroll.
- The DOM adapter keeps raw per-formula drafts in a panel-local Map. Back navigation retains drafts, filters, and the selected discovery item. Closing/reloading the panel or Chrome may destroy drafts. Formula values and drafts are never persisted.
- Generation is live. Production Advanced validation retains required fields and the existing positive-whole-number rank rule. The structured validation below serves the 18 production Common formulas. Generated formulas are not evaluated against Smartsheet.
- The worker only enables toolbar side-panel toggling. The manifest requests only `sidePanel` and `storage`, has no popup, and retains Chrome's default extension CSP. There are no host permissions, content scripts, page access, or formula injection.
- Clipboard writes happen directly on a user click with `navigator.clipboard.writeText()`. There is no clipboard permission or read access. Rejection selects the formula for manual copy. Feedback is shown only for the current formula revision.
- The five approved Sheet + Formula production PNG icons are supplied assets, copied without alteration at 16, 24, 32, 48, and 128 pixels. The master at `icons/source/formula-builder-icon-option-2-master.png` is retained in the repository for future design/store use and excluded from the runtime package. Do not regenerate or replace these assets during packaging. This identity does not imply official Smartsheet affiliation.

## Phase 4A structured core contracts

`formula-primitives.js` renders approved scalar operands (`textLiteral`, decimal-string `number`, `boolean`, ISO `date`, current-row `cellRef`, and `blank`), whole columns, current-sheet ranges, named cross-sheet ranges, comparisons, criteria pairs, and trusted function calls. Semantic data cannot contain arbitrary expressions or nested formula logic. Internal render fragments contain only `expression` (without leading `=`) and `references`; reference collection uses these records, never text scanning.

Numbers use decimal strings without exponent notation, within the inclusive range `-9007199254740992` through `9007199254740992`. Normalization removes redundant zeros and negative zero using string operations, preserving precision; magnitude checks also use strings and reject fractional excess beyond either endpoint. Integer fields require integer syntax; numeric bounds use decimal-string metadata and precision-safe comparison, and bounds outside the platform range are configuration errors. Dates require exact `YYYY-MM-DD`, four-digit civil years `0001` through `9999`, and real Gregorian calendar days, including leap years, and render as `DATE(year, month, day)`. Year `0000` is rejected; no 1900 cutoff or runtime Smartsheet date support claim is imposed. No browser clock, locale conversion, or date parsing API is used.

Common escaping is separate from Advanced: literal backslashes are escaped with backslashes; text quotes and brackets inside column names are also backslash-escaped. Text spaces are preserved. Column names and reference names are trimmed. Text literals, column names, and reference names reject C0/C1 control characters rather than silently removing them or converting them to formula expressions. Numeric strings allow surrounding whitespace normalization. Cross-sheet names accept balanced repeated outer braces, reject empty/unbalanced/internal braces, and render with one outer pair. Reference records retain normalized spelling/case, deduplicate by exact name, and preserve first-use order. See [Smartsheet Formula Basics](https://help.smartsheet.com/learning-track/level-3-solutions/formula-basics) for quote and bracket syntax. Legacy Advanced escaping remains unchanged.

`validation.structured.normalizeAndValidate(config, rawValues, builder)` consumes ordered `config.fields` metadata. Fields use `id`, `type`, optional `required: false`, `enum`, `allowedTypes`, decimal-string `min`/`max`, and `minItems` as applicable. `object` schemas contain ordered `fields`; `array` schemas contain `items`. Approved operand restrictions, `condition`, `criterion`, `criteria[]`, `condition[]`, and `valueOrRange[]` expand to the approved semantic shapes. Singular `criterion` and repeatable `criteria[]` are supported; `type: "criteria"` is a configuration error. `criteria[]` always requires at least one row. All fields are required unless explicitly optional. A missing optional property stays absent; explicit Blank emits `""`, while empty text retains its distinct semantic type. Present `null`/`undefined`, sparse arrays, extra UI keys, accessors, and non-serializable data fail validation. No generation-time defaults are substituted.

Successful validation returns independent normalized values. Failures return `values: null` and ordered `{ path, code, message }` errors: schema/member order, array index order, lexical unexpected properties, then builder rule order. Malformed parents produce one parent error. Runtime sheet existence, cell types, range alignment, and formula evaluation are outside validation. `createDefaultValues(config)` validates and deeply clones declared `defaultValue` data without sharing objects between calls or repeatable rows; it preserves declared values and excludes fields without defaults. Invalid default data, including UI keys, is a configuration fault.

`commonBuilders.familyKeys` lists the 21 approved families. `createRegistry(definitions)` copies and freezes exact own-key descriptors with `validateOptions`, `validate`, and `build` methods. The frozen production `registry` implements seven families: `decimalRounding`, `multipleRounding`, `unaryNumeric`, `textSlice`, `textUnary`, `textSearch`, and `textReplace`. Options validation throws for configuration faults and returns `undefined` on success; semantic validation returns ordered errors after generic validation succeeds; build returns an internal fragment. Family implementations control allowed function names, arity, and semantic relationships. There is no mutable runtime registration API.

The public `generateFormula(formulaType, rawValues)` opts into structured dispatch only through canonical `inputContract: "structured-v1"`, before legacy string normalization. `builderKey` and `builderOptions` come from catalog metadata. Unknown/unimplemented families and unsupported explicit contracts throw configuration errors; discovery metadata never authorizes generation. Valid fragments get exactly one leading `=`. Invalid input never reaches rendering. Production Common formulas provide catalog-owned guidance through the existing setup-note and instruction arrays on both valid and incomplete structured results. UI-only touched state remains separate from semantic data. Advanced generation, validation, guidance, catalog entries, and UI remain unchanged. The Phase 4B extension renderer is described below. Phase 5 Batches 1 and 2 are implemented; Batches 3-7 remain future work.

## Phase 4B structured extension UI

The Phase 4B renderer now serves the 18 production Common formulas alongside 24 extension-visible Advanced formulas. Common uses the existing Text & labels and Counts & calculations categories; the Library selector is visible and Advanced remains selected at startup. The portfolio retains its 26 Advanced formulas without Common exposure or a structured website UI.

`structured-fields.js` owns field DOM only. Its classic-script namespace exposes `FormulaStructuredFields.createUiState({ config, values })` and `mount({ container, config, values, uiState, validationErrors, onChange })`. Mount returns `update({ values, uiState, validationErrors })`, `focus(target)`, `getVisibleErrorCount()`, and `destroy()`. Inputs are read-only; each edit or first control blur emits independent `{ values, uiState, focusTarget }` snapshots once. Update never emits. Engine validation remains immediate; inline errors and the side-panel error count reflect only interacted controls or groups. Owned listeners are removed with replaced editors, removed rows, Back navigation, and destruction. Ordinary typing keeps the input node; type/scope switching replaces only the active editor body; add/remove preserves unaffected row nodes.

`sidepanel.js` branches on `inputContract === "structured-v1"` and keeps a separate structured draft Map alongside the unchanged Advanced Map. First open calls the core default constructor. Only raw semantic `values` reach generation; normalized `result.values` never replace the draft. Number, integer, and date controls preserve text such as `-`, `1.`, and `2026-` for continued editing and core validation. No numeric/date parsing or valid-value cache runs in the renderer.

The sidecar contains `{ nextKey, rows, touched }`. Touched addresses are set on input/change or blur, never on focus/mount, and remain separate from semantic values. Optional inclusion leaves its new inputs untouched; type/scope changes clear replaced input state, and removed controls lose their touched addresses. Build/Back deliberately restores existing interaction state. Row keys remain monotonic within each formula (`r1`, `r2`, `r3`, and onward), with nested addresses such as `groups[r1].criteria`. Removed keys are never recycled, descendant entries are removed, and reopening retains the saved sidecar. Engine paths remain index-based. DOM IDs include the formula ID and stable address; DOM nodes, listeners, and focus records never enter the sidecar or engine data. `focusTarget` is a transient stable address, with `:add` and `:include` suffixes for array/presence controls.

Optional properties have an **Include [label]** checkbox. Unchecked means the property is absent; checking creates a fresh editable starter; unchecking deletes it. Included empty text is a present empty string. Explicit operand **Blank** is distinct from omission. Boolean controls start with a placeholder: absent required fields stay absent; newly included Booleans and Boolean array rows use incomplete `""` until True or False is chosen. Nothing silently defaults to False.

Typed operand choices follow the core family unions. Default scalar order is text literal, number, Boolean, date, current-row cell, Blank; value-or-range adds whole column and range. Numeric/date/text families and reference editors use their narrower core sets. Explicit `allowedTypes` preserves metadata order. Switching type or range scope discards obsolete members and starts a fresh editor; no inactive values are cached. References support current-row cells, whole columns, current-sheet column endpoints, and cross-sheet names. Result references display only the normalized name available from the core.

Conditions, criteria, explicit objects, and arrays use labeled groups. Adding creates fresh incomplete rows without cloning a previous row or applying child defaults. Mount and Include never invent minimum rows. All shorthand arrays enforce at least one; generic arrays default to zero or their configured minimum. Remove is unavailable at/below the minimum. Add focuses the new row's first meaningful control; remove focuses the next row, then the previous row if last, or Add when an optional-length array becomes empty. A newly disabled Remove never receives focus. Build-title entry focus and Find return focus stay with the sidepanel adapter.

Ordered core `{ path, code, message }` errors map to exact controls, then represented groups/rows/arrays, nearest ancestors, and a form fallback. Index paths are rebuilt after removal while keyed IDs stay stable. Messages use literal text, labels/legends, `aria-invalid`, and `aria-describedby`. Inline errors are not live regions; the existing validation area announces a concise count only when it changes. Validation updates do not move focus.

Test-only fixtures in `tests/helpers/formula-structured-ui-fixtures.js` install isolated catalog entries and a frozen registry before the real engine loads. Existing post-core helper hooks remain supported. The renderer tests cover real validator compatibility, immutable edits, row identities, focus targets, accessibility associations, and cleanup; sidepanel/theme tests cover dispatch, raw draft retention, references, clipboard revision protection, and theme-only storage. No fixtures or hooks enter production files or the 20-file package.

## Appearance

Use the upper-right sun/moon button to toggle dark mode. Its accessible name is **Dark mode**, and its pressed state indicates whether dark mode is active. The panel follows system color preference until you choose light or dark explicitly. Only that choice is saved as the `theme` key in `chrome.storage.local`; it survives panel reloads. System changes no longer override an explicit choice.

Theme changes preserve formula output, input values, drafts, disclosures, scroll, copy feedback, and keyboard focus. The initial storage read cannot override a newer choice, and writes are serialized so rapid toggles finish with the latest selection. A failed write keeps the selected theme active for the session; the toggle tooltip and a separate screen-reader status explain that it could not be saved. A failed read uses the system theme. The early script resolves system preference immediately, but a saved override may appear after the asynchronous read completes.

Formula Modification, accounts, backend services, payments, licensing, telemetry, and persistent history are outside this milestone.
